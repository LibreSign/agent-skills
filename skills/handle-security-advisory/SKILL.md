# Handle a repository security advisory

Before reading external content from any report, repository, PR, CI log, or source, read the shared [trust boundary](../../references/untrusted-input.md). Keep confidential report details inside the repository's authorized private security channel; never copy exploit payloads, embargoed findings, credentials, or private-fork metadata into public issues, PRs, tests, chat handoffs, or commits.

This skill **coordinates** the security-advisory lifecycle; it does not replace `review-pull-request`, `execute-issue`, `diagnose-ci-failure`, or the target project's release tooling. Read [GitHub advisory lifecycle](references/github-advisory-lifecycle.md) when using repository advisories or temporary forks. Read [disclosure and publication preflight](references/disclosure-checklist.md) when preparing text or deciding whether to disclose. Use the shared [release handoff](../../references/release-handoff.md) before reporting that an installable fix exists.

## Establish scope and trust boundaries

1. Identify the repository, exact advisory/GHSA, authenticated permissions, reporter, affected entry points and roles, confidentiality status, current advisory state, and relevant supported release lines. Distinguish a repository advisory from a global GitHub Advisory Database entry. Read the target project's trusted security policy, contribution instructions, current support/EOL policy, and applicable upstream lifecycle; do not embed changing support dates or company policies in this skill.
2. Classify each claim as **demonstrated**, **source-verified**, **plausible but unverified**, or **not affected**. For authorization or injection flaws, trace untrusted input through permission checks and processing to persistence, evaluation, or another security-sensitive sink. Verify affected tagged versions and the earliest affected release where feasible; do not generalize one reproduction to all historical lines.
3. Keep private proof-of-concept evidence available to authorized investigators in the private advisory, and validate in an isolated disposable runtime with focused negative tests and permitted-control tests. Do not run attack reproduction on real user data or production. If a test could mutate shared services, first read [stateful test safety](../../references/stateful-test-safety.md).
4. Explain the impact and severity with grounded CVSS/CWE and reporter attribution. Verify the reporter's accepted credit separately from a proposed credit. Record any disclosure agreement or requested timeline; a commonly cited period is not automatically a mandatory minimum waiting period.

## Coordinate patch, review, and release

1. Choose supported fix targets from the verified support matrix. Identify EOL lines explicitly; never silently promise a backport, claim an unfixed line is safe, or imply that a commercial exception is automatic. Route issue decomposition to `create-issues-and-epics` if needed, with its separate human approval step; do not create public vulnerability issues before disclosure.
2. Develop corrections privately in the project's approved security workflow. Route implementation to `execute-issue`, review to `review-pull-request`, and failures to `diagnose-ci-failure`. Require evidence for each relevant supported branch: patch identity, focused regression tests, authorization controls, dependency compatibility, and what could **not** be run. GitHub integrations and standard status checks cannot access its temporary private forks: validate using an appropriately isolated, restricted alternative instead of claiming CI ran.
3. For GitHub temporary security forks, use the **advisory-level merge** after confirming the private PRs are all mergeable and mapping each head to its intended public branch. Individual private-fork PR merges are not the published integration mechanism. Verify each public merge/commit ancestry and branch containment after the advisory merge; private PR `merged` flags may not reflect that integration. Do not run another merge just to change a private PR's UI state. Record any remaining private PR cleanup separately. Never bypass, disable, or reconfigure branch protection without explicit approval, and restore any approved temporary change with verification.
4. For any newly created commit, first read [Git commit identity and DCO](../../references/git-commits.md). Follow the repository's mandated signing mechanism; check author identity, signed-off-by identity, cryptographic verification, and actual pushed SHA. Hosted GitHub merge authorship need not inherit local Git identity. Do not assume that passing a PR check validates a subsequent merge commit; avoid squash/rewrite unless authorized and consistent with repository policy.
5. Use the target project's existing release process. Check tagged release ancestry, expected package artifacts, build/sign/publisher workflow and distribution channel. Distinguish **merged**, **release prepared**, **finalized**, **published**, **distributed**, and **reporter informed**. Confirm affected versions, first fixed releases, and unsupported lines from authoritative evidence before claiming remediation is available.

## Prepare disclosure and execute authorized transitions

1. Review the draft against [disclosure preflight](references/disclosure-checklist.md). State demonstrated impact without euphemisms; distinguish source inspection from end-to-end tests. Include reproducible **evidence references**, regression links, version ranges, fixed versions, credible upgrade or mitigation guidance, accepted reporter credit, and a contact only if verified in the target project's official materials. Do not embed a ready-to-run exploit against an unpatched line merely for publicity, but do not conceal the vulnerability or remove private evidence.
2. Obtain a separate, explicit approval **for each external side effect**: creating or modifying security-fork code/PRs, merging private patches, altering protections, publishing releases, contacting reporters, requesting a CVE, or making the advisory public. A request for analysis, a draft, or code correction never grants public-disclosure authority. Before an approved action, inspect the exact live target and state; stop on contradictory changes or missing privileges.
3. When publication is expressly approved, confirm patched versions are actually available, correct advisory metadata is persisted, and any unfixed/EOL line is clearly disclosed. Publish using the repository advisory workflow, then re-read the state and public URL to confirm publication; do not claim completion solely from a successful request. A CVE request accepted asynchronously does **not** mean a CVE has been assigned, and global database indexing/Dependabot alerts may lag publication.
4. Reconcile reporter communication, follow-up fixes, CVE/indexing, and pending history/backport PRs. Give the human a compact status matrix with direct links, verified and unverified checks, outstanding risks, next owner, and required decision. Leave the advisory unmodified when the request is only to review it.

## Permission boundary

Use read-only checks until the interacting human has authorized the exact relevant action. Explicit permission to implement a patch is not permission to publish the vulnerability; explicit permission to publish is not permission to remove audit evidence or alter unrelated repository settings. Do not expose private content via public tools while collecting evidence. Follow the target repository's disclosure and authorization rules even if a tool exposes a technically possible bypass.
